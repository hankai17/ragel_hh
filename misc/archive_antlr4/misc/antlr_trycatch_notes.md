# ANTLR 用 try/catch 表示解析匹配失败，是不是太重？——问答总结

> 归档说明：本文总结自一次设计评审问答。背景是 antlr4_hh 规则引擎的
> `rule_check_text` 滑窗匹配，以及为消除 O(n^2) 放大而做的
> "BailErrorStrategy 快速失败 + 尝试/耗时预算"修复。

## 1. 背景

- 规则插件由 rulec 从 `.g4` 生成：`rule_check_text` 对归一化文本做共享词法，
  然后在每个可见 token 起点、对每条攻击规则尝试解析（滑窗重解析）。
- 修复前最坏路径：失败尝试走默认错误恢复，`recover()` 对顶层起始规则算出的
  恢复集为空，`consumeUntil` 一路吞到 EOF，单次失败成本 O(n-i)，滑窗叠加成
  O(n^2)。
- 已实施修复（提交 `8fb26ca`）：每次尝试设置 `BailErrorStrategy` + `try/catch`
  （首个错误立即抛出，不吞 token），并给单次 `rule_check_text` 加尝试数预算
  （1024）与耗时预算（5ms）。

实测（同一 Debug 构建、单次进程调用含 dlopen/初始化开销）：

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 良性 fast path（hello world） | 4 ms | 3 ms |
| 良性 SQL 深检（WHERE id=1） | 6 ms | 7 ms |
| 1=1 × 1000 | 1544 ms | 72 ms |
| 1=1 × 2000 | 6446 ms | 134 ms |
| `;` × 1000 | 78 ms | 46 ms |
| `x=1` × 1000 | 2036 ms | 74 ms |
| `1=1;x` × 500 | 1183 ms | 59 ms |

校验 48/48 通过，`1=1`×2000 仍正确命中 `always_true` -> BLOCK。

## 2. 问题

> "antlr这种 靠try catch机制 来表明解析匹配失败 这种做法太重了吧"

即：在"匹配失败"是主路径（几乎每次滑动尝试都失败）的 WAF 深检场景里，用异常
做控制流是否成本过高、是否设计不当。

## 3. 结论先行

直觉是对的：**异常作为高频失败信号确实是重的**。修复后对抗输入仍比良性深检贵约
20 倍，剩余开销主要就是每尝试的 parser/simulator 堆分配、上下文节点分配和异常
throw/unwind。但这是 ANTLR 架构下唯一简单且必然正确的失败通道；正解不是绕开
异常，而是**同时降低失败频率和单次失败成本**。

## 4. 详细回答

### 4.1 为什么 ANTLR 只能这样

- ANTLR 生成的规则函数是递归下降代码，`match()` 成功时返回 token，**失败时没有
  返回值通道**——错误信号只能靠异常从任意深度的嵌套调用中"炸"出来。
- `Parser::match()` 的 C++ 实现里，token 不匹配就走 `_errHandler->recoverInline()`，
  而默认/BAIL 策略的实现都是 `throw`。这是代码生成器的唯一错误通道，不是可配置项。
- `BailErrorStrategy` 就是 ANTLR 官方为此提供的"快速失败"工具；Java/C#/C++ 版
  一致，yacc 系解析器也普遍用异常处理语法错误。

### 4.2 成本构成

- 零成本异常处理（Itanium ABI）：**没抛时 try 块几乎零开销**，成本只在 throw。
- 每次 throw：异常对象分配 + 栈展开 + handler 查找 + 沿途析构，通常几百 ns 到
  几 µs，取决于栈深。
- 本项目规则函数栈很浅（2~3 层），单次 unwind 便宜，但**频率高**：尝试预算
  1024 即最多 1024 次 throw/调用，再叠加每次尝试两次堆分配，构成对抗输入的主要
  剩余成本。

### 4.3 更轻的替代方案（按激进程度排序）

| 方案 | 思路 | 代价 / 风险 |
|---|---|---|
| 自定义短路错误策略 | 重写 `recoverInline`：首次错误只置失败标志并返回当前 token，后续 `match()` 走 `inErrorRecoveryMode` 快速返回，规则"跑完"后 wrapper 查标志 | 单次失败降到 O(规则长度) 的 token 检查、无异常展开；但 match 不消费 token 时 `(expr)*` 类循环会原地打转，必须保证 token 推进（failsafe consume）。能做，但要小心 |
| 减少失败频率 | 尝试预算已封顶；进一步按规则记录"下一个候选位置"、更细的首 token 索引，砍掉无谓尝试 | 无风险，收益有限 |
| parser 对象池 | 用 `reset()` 复用 parser/simulator，省掉每尝试两次 `new` | 需处理异常路径下的 reset 保证（RAII 或 finally） |
| 热门规则手写匹配器 | 碎片规则形态简单，手写 token 级匹配器用返回码表达失败 | 最快，一个数量级以上；但规则集分裂成"ANTLR 规则 + 手写规则"，失去"安全人员只写 .g4"的产品定位 |

### 4.4 判断与建议顺序

- 当前 "bail + 预算" 是正确取舍：异常是框架既定机制，改造风险高，预算已把异常
  频率限制死。
- 若产品需扛真实高 QPS 且对抗输入占比不可忽略，下一步顺序：
  1. parser 对象池（去每尝试堆分配）；
  2. 自定义短路错误策略（去异常展开，注意循环进度保证）；
  3. 热门规则手写匹配器（终极手段）。
  每一步用 `misc/bench_sqli.sh` 前后对比验证。
- 最终目标不是"消除异常"，而是**让最坏输入的开销接近良性输入**——需要把
  每尝试分配、异常、跨插件重复分词一起降下来。
